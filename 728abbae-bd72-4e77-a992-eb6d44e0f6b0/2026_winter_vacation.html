大学最后一个寒假就这么结束了(其实正式开始写本文时已经开学两周了1). 这学期回来之后就得准备毕业论文, 理所当然地感慨(后悔)假期都干嘛了(怎么没学习). 所以, 本文用于记录 2026 年寒假期间的更换 WSL 中 Linux 发行版(主要)以及配置 Emacs (次要)的记录. 这不是一篇技术向的分享, 只是随便记录一下生活.

1. 背景&引子

我去年2六七月开始用 WSL, 最初安装的发行版是 Ubuntu, 后来很快换到了 Debian; 去年九月开始热衷于配置 Emacs3, 到现在也算是攒了一份自己的配置. 在使用 Debian 的过程中, 我发现 apt 源涵盖的包貌似相对较少, 部分包需要用 apt 之外的方式安装; 在去年十二月和今年一月上旬, 我还遇到了 Stable 源中包相对较旧的问题. 后来为了用最新的 Emacs 添加了 Sid 源, 但是因为没有全部切换为 Sid, 后来遇到了(可能由)不同源混用引起的依赖冲突问题.

这里我真的忍不住想单列一段说一下这次遇到的依赖冲突, 因为看起来还挺好玩的, 具体表现为某个包的一个依赖和它的另一个依赖的依赖冲突: 某个第三方包 A1 依赖 B1 和 B2, B2 依赖 C1, 然后 C1(来自 Sid, 版本较新) 跟 B1(疑似来自 Stable, 版本较旧) 冲突(因为二者版本不同), 同时 B1 和 C1 好像都(也可能是其中之一)被别的包依赖, 没法通过简单的重装低版本处理冲突.

2. WSL: 从 Debian 到 NixOS

2.1. 告别 Debian

一月上旬中旬因为忙着准备期末考试啥的, 没有太多精力放在这些上面, 到了一月下旬放假回家才拿出精力来处理(玩)这些. 虽然依赖冲突的原因可能在于我不太好的使用习惯 (Stable 和 Sid 混用), 但是我最初添加 Sid 的动机是 Stable 中的包比较旧4, 再加上之前使用 Debian 的过程中有几次需要安装的包在源中不存在最后只能用脚本安装5, 这些原因让我期待换一个滚动更新或者接近滚动更新, 并且源中含有较多包的 Linux 发行版.

2.2. 一头撞死在 Arch 上

正巧寒假刚开始不久, 我玩性大发(不知天高地厚(bushi))就想尝试传说中的 Arch Linux, 结果到最后只能说一句: "Arch Linux, 感谢这一两天里你的戏份". 在短时间内放弃 Arch, 原因是使用过程中遇到了一些我无力解决的问题, 比如 systemd 报错, Emacs GUI 也莫名其妙挂掉(大概是没配置好 WSLg 相关). 最后怎么也弄不好6, 只能无奈删除.

但说实话, 相比之前用 Ubuntu/Debian, 这次短暂的体验也算是让我看到了 Arch 的魅力, 包括但不限于设计上的 KISS 原则, 安装和配置过程中的透明化, AUR, 等等. 但对于现在的我来说, 没有太大的动力和需求去学习 Linux 的系统架构和工作原理, 还是一些相对新手友好和开箱即用的发行版更适合现在的我, 毕竟我当前使用 WSL 主要是为了使用 Emacs, 在学习 Linux 方面动力有限.

2.3. 折中的 openSUSE Tumbleweed

在 Arch Linux 那里撞墙之后, 本着滚动更新+少修系统这两个原则, 经过了和 AI 的多番讨论和简单的调研, 我决定试一试 openSUSE Tumbleweed. 在包管理器上, zypper 和 apt 在使用方法和上很接近(和 pacman 区别明显), 但包比 apt 更多更新. 除了少数几个包名的差异, 用 Debian 时维护的初始化脚本在 openSUSE 中基本也能沿用. 在使用便捷性上, 我个人感觉开箱即用的程度和 Debian 差不多, 对不想在系统调试上花费太多精力的 or 不会调试系统的人来说比 Arch Linux 方便一些. 看起来 openSUSE Tumbleweed 已经是我这次换发行版之旅的终点了.

2.4. 拥抱 Nixos7

我接触到 NixOS 是一个意外8, 但简单了解之后我发现 NixOS 声明式配置与原子化升级与回滚的特性解决了一个一直被我忽视的痛点: 命令式配置系统的可复现性依赖自行维护的"配置笔记"或者"初始化脚本", 这一般是有关操作(比如包的安装)的指令记录, 而它们的效果常常依赖于执行命令时所处的系统环境(比如版本), 从而在一定程度上违背了维护它的最初目的; 自行维护的初始化脚本对我来说很不方便进行测试, 我几乎不可能每次修改脚本都通过安装一个新的系统来测试脚本运行能否实现预期. 这些问题都在 NixOS(启用 flake 特性) 中得到了解决.

在声明式配置以外的其他方面:

  • 社区中提供的 NixOS-WSL 解决了 Microsoft 官方没有在 WSL 提供 NixOS 的问题;
  • 得益于我从使用 Emacs 开始深度使用 WSL, 结合 Git 管理的声明式配置反而比命令式配置更符合我的习惯, nix 语言的上手也并不比 elisp 更难, 而 NixOS 提供的配置选项也足够丰富, 查 nixos-option 和 home-manager option 编写 Nix 配置文件可以满足我的绝大部分需求;
  • 没有依赖冲突问题;
  • nixpkgs 提供的包足够丰富, 版本也并不落后.

总而言之, 至少截至本文发布时, NixOS 充分契合了我(又菜又爱玩)的需求, 既方便我以自己习惯的方式折腾9, 又有充分的兜底机制防止我轻易把系统搞挂掉, 在最后的最后还能用经验证可用的配置文件重装.

3. 更换发行版遇到的一些的事情

有关 keys, 其实主要是 gpg. 最开始用 gpg 的时候没有彻底理解它, 一开始我以为 gpg 应该像 ssh 一样, 密钥跟着主机/系统走, 所以之前换发行版的时候每个发行版一个 gpg 密钥. 后来大概是使用 openSUSE 的后期意识到 gpg 应该跟着账户/跟着人走, 但是此时 GitHub 上已经塞了多个公钥了. 最后将 openSUSE 里用的那个 gpg keys 导入到 NixOS 中, 然后归档了一批私有仓库(其实就是当时主要用的几个), 新建了两个公开仓库分别放我的 Emacs 配置文件和 NixOS 配置文件, 好像还做了一部分 rebase 重新签名10.

有关 docker container, 为了方便我在不同发行版中适用的目录结构相同, 但忽视了容器挂载的 volume 是绑定发行版的, 导致有几天我怎么都没法用容器中的 texlive 编译, 但是查容器中对应的命令都存在. 后来注意到这个问题在主要工作的发行版中重建容器就好了.

有关 VSCode, 说来奇怪, 用 NixOS 之后我的 VSCode Remote-WSL 时灵时不灵的, 即使我用了 nixos-vscode-server. 这算是一个小缺点吧, 但是我现在完全不用 VSCode 了, 基本都在 Emacs 中编辑, 所以也还好.

4. Emacs: 改配置只道是寻常

寒假期间好像没什么太多有意思的值得拿出来说的 Emacs 配置变更, 但是因为这又是我一直在做的事情, 所以就根据印象说说吧:

  • 添加了包括 markdown-mode yaml-mode nix-mode 在内的一些常见语言的支持, 主要是为了方便高亮与缩进;
  • 将 org-roam-organize 有关功能转移到单独的仓库中, 在配置中作为一个包被使用11;
  • 因为听说 Org 最新版本发布了换成最新版本, 之后才发现有关 org-latex-preview(来自这个) 的功能好像还没合并到主分支, 然后又滚回原来的版本了;
  • 虽然是 <2026-03-01 Sun +0800>–<2026-03-02 Mon +0800> 的 commit, 严格来说不算寒假期间了, 但是还是想提一嘴, 主要基于 org-roam-db-query 获取需要 publish 的文件列表, 优化了 blog publish 的流程.

5. 结语

回顾整个寒假, 我一直在努力打造一个好用的 WSL 和好用的 Emacs, 一个月里换了三次发行版, 也是挺值得记录的一件事情了. 事实上我研究工具本身远比使用它们多, 但考虑到"折腾"本身就能带给我很多快乐, 所以也合理.

另外, 因为开学之后有点焦虑, 一直每太有写东西和分享的心情, 导致这篇文章一直拖到现在(三月中旬)才发出来. 之前我还想着差不多每个月更一篇, 现在看来本学期是真的不定期更新了.
